#### 먼저 읽을 것 — 질문 구조와 세션 진행

AI 파트 설계 내용. 다른 파트가 구현 전에 알아야 하는 것을 모아놓음.
급하면 마지막 15만 읽어도 됨.

용어 — 문서에서는 **친절형 / 압박형**으로 쓰고,
API 값은 `friendly` / `pressure`를 그대로 사용한다.

---

## 1. 주질문과 꼬리질문

면접은 **토픽** 단위로 진행된다.
한 토픽은 주질문 1개 + 꼬리질문 0~2개로 구성된다.

```
토픽 1
  주질문    프로젝트 중 가장 기억에 남는 것을 소개해 주세요
  꼬리질문  왜 낙관적 락을 선택하셨나요?
  꼬리질문  요청이 몰리면 재시도 비용이 커지는데, 적절했나요?
```

둘은 만드는 방식이 다르다.

```
주질문    이력서만 보고 만든다. 면접 시작 전에 미리 생성 가능
꼬리질문  직전 답변을 읽고 만든다. 실시간 생성만 가능
```

**꼬리질문이 실시간으로 만들어지는 것이 이 서비스의 핵심이다.**
미리 만들어둔 질문 목록에서 고르는 방식이 아니다.

## 2. 난이도 3단계

난이도는 "쉽다/어렵다"가 아니라 질문이 요구하는 작업의 종류로 정의한다.

```
L1  사실 확인      이력서에 적힌 내용을 확인한다
                  예) 그 프로젝트에서 어떤 부분을 담당하셨나요?

L2  근거 요구      선택의 이유와 판단 과정을 설명하게 한다
                  예) 그 기술을 선택하신 이유는 무엇인가요?

L3  전제 흔들기    답변의 가정에 반박하고 방어하게 한다
                  예) 그 방식은 요청이 몰릴 때 비용이 커지는데,
                      적절한 선택이었나요?
```

**사용자는 난이도를 고르지 않는다.** 페르소나만 고르고 시스템이 배분한다.
사용자는 L2와 L3의 차이를 알 수 없고, 난이도 3을 골랐는데 첫 질문이
쉬우면 불만이 생기기 때문이다.

```
친절형   L1에서 시작해 천천히 올라간다
압박형   L2에서 시작해 빠르게 L3로 간다. 마지막 질문은 항상 L3
```

## 3. 카테고리 8종

```
지원동기      직무역량      프로젝트경험    문제해결
협업·갈등     실패·성장     가치관·인성     미래계획

주질문    우리가 카테고리를 지정해서 생성한다 (커버리지 보장)
꼬리질문  LLM이 자유롭게 만들고, 나온 질문에 태그만 단다
```

꼬리질문에 카테고리를 강제하면 대화가 부자연스러워진다.
협업 이야기 중에 갑자기 미래계획을 물으라고 지시하는 꼴이 된다.

**문자열은 가운뎃점(·)까지 정확히 일치해야 한다.**
`협업·갈등`을 `협업`으로 쓰면 API에서 오류가 난다.

## 4. 문항 수와 토픽 수

```
3문항 → 2토픽
6문항 → 3토픽
9문항 → 4토픽
```

각 토픽에 몇 문항을 배정할지는 미리 준비된 패턴 중 무작위로 고른다.
`[2, 2, 2, 3]`이면 앞 세 토픽은 주질문+꼬리 1개, 마지막은 주질문+꼬리 2개다.

패턴 전체 목록은 7 참고.

## 5. 답변 판정 — 2단계

답변이 충분한지 부실한지 판단해서 다음 행동을 정한다.
비용과 정확도를 함께 잡기 위해 두 단계로 나눈다.

```
1단계  길이 게이트
       발화 10초 미만 또는 25어절 미만이면 명백히 부실하다
       LLM을 부르지 않고 바로 되묻는다

2단계  LLM 판단
       1단계를 통과한 답변만 LLM이 읽고 판정한다
       sufficient    파고들 내용이 있다 → 꼬리질문 생성
       insufficient  부실하다 → 되묻는다
       escalate      매우 충실하다 → 난이도를 한 단계 올린다
```

**1단계가 있는 이유**
"네." 한 마디짜리 답변에 LLM을 호출할 필요가 없다.
명백한 케이스를 먼저 걸러 비용과 대기 시간을 줄인다.

**2단계가 있는 이유**
길이만으로는 잡히지 않는 답변이 있다.
길게 말했지만 알맹이가 없거나 주제에서 벗어난 경우가 대표적이다.
이건 내용을 읽어야만 판단할 수 있다.

### 제한 시간으로 잘린 답변은 판정하지 않는다

답변 제출에 `is_timeout` 필드가 온다.
true이면 길이와 무관하게 되묻지 않고 다음 질문으로 넘어간다.

시간이 끊은 답변에 "조금 더 말씀해 주시겠어요"라고 되묻는 것은 오작동이다.

### 채점기를 쓰지 않는다

내용 판단은 하지만 **채점 모듈은 거치지 않는다.**
꼬리질문 생성 프롬프트가 답변을 읽는 김에 함께 판정한다.

```
{
  "question": null,
  "verdict": "insufficient",
  "reask": "어떤 기술을 사용하셨는지 조금 더 말씀해 주시겠어요?"
}
```

채점기로 질문 흐름을 정하면, 채점이 틀렸을 때 질문도 같이 틀어져서
원인을 분리할 수 없다. 질문 생성기가 내리는 판단은 채점 결과와
독립적이므로 이 문제가 없다.

**되묻기 문구도 LLM이 만든다.**
고정 문구 대신 무엇이 빠졌는지 짚어서 물을 수 있다.

**검증이 필요한 항목**

LLM 판단은 일관성 확인이 필요하다.
같은 답변을 여러 번 넣었을 때 판정이 갈리면 쓸 수 없다.

앵커 답변 세트 5종(높음 / 중간 / 낮음 / 유창하지만 주제이탈 /
짧고 불충분)으로 반복 판정 테스트를 진행한다.

**검증 전까지는 1단계만 사용한다.**
LLM 판정 없이도 세션은 정상 진행되며, 문항 수도 보장된다.
verdict를 넘기지 않으면 모든 답변이 sufficient로 처리된다.

## 6. 문항 수는 반드시 지켜진다

부실한 답변으로 꼬리질문이 생략되면 예비 토픽을 투입해 채운다.
사용자가 9문항을 선택했으면 어떤 경우에도 9문항이 나간다.

```
잘 답할수록        토픽이 적고 깊게 들어간다
부실하게 답할수록  토픽이 많고 넓게 훑는다
```

## 7. 배분 패턴 전체 목록

세션 시작 시 아래 중 하나를 무작위로 고른다.
배열은 각 토픽의 문항 수다.

```
3문항 / 2토픽
  점층형   [1, 2]        가볍게 열고 두 번째 주제를 파고든다
  집중형   [2, 1]        첫 주제를 파고들고 두 번째로 넓힌다

6문항 / 3토픽
  점층형   [1, 2, 3]     뒤로 갈수록 깊어진다
  균형형   [2, 2, 2]     세 주제를 고르게 다룬다
  집중형   [3, 2, 1]     초반에 깊이 파고들고 후반은 넓게

9문항 / 4토픽
  점층형    [1, 2, 3, 3]  도입은 짧게, 후반 두 주제를 깊게
  균형형    [2, 2, 2, 3]  고르게 가다 마지막에 심화
  집중형    [3, 2, 2, 2]  첫 주제에서 깊이 확인 후 균등
  중반강화  [2, 3, 2, 2]  핵심 역량 주제에서 집중
  대비형    [1, 3, 3, 2]  도입과 마무리는 짧게, 중간을 깊게
```

경우의 수를 전부 쓰지 않고 선별했다.
마지막 토픽이 1문항으로 끝나는 배분은 면접이 흐지부지 끝나는 인상을 주고,
깊이가 들쭉날쭉한 배분은 파고들다 갑자기 넘어가는 흐름이 되기 때문이다.

## 8. 카테고리 슬롯

토픽 위치마다 뽑을 수 있는 카테고리가 정해져 있다.

```
토픽1  도입     지원동기
토픽2  역량     프로젝트경험 | 직무역량
토픽3  인성     협업·갈등 | 실패·성장
토픽4  마무리   미래계획 | 가치관·인성
```

토픽 수만큼 앞에서부터 사용한다.
슬롯마다 하나를 뽑으므로 세션마다 조합이 달라진다.

배분 패턴까지 곱하면 9문항 기준 5 × 8 = 40가지가 되어,
같은 이력서로 여러 번 봐도 같은 면접이 되지 않는다.

문제해결은 슬롯에 없다. 프로젝트경험을 파고들면 자연히 문제해결로
이어지므로 꼬리질문에서 태그되도록 둔다.

## 9. 난이도 배분 규칙

토픽 안에서 질문이 진행될수록 올라가고, 뒤 토픽일수록 시작점이 높다.

```
친절형   전반부 토픽은 L1에서 시작, 후반부 토픽은 L2에서 시작
압박형   첫 토픽만 L1에서 시작, 나머지는 L2에서 시작
         단 토픽이 2개뿐이면 첫 토픽도 L2에서 시작
         세션 마지막 질문은 항상 L3
```

실제 생성 결과다.

```
3문항 친절형  [2,1]      L1/L2  L2                 L1:1 L2:2 L3:0
3문항 압박형  [2,1]      L2/L3  L3                 L1:0 L2:1 L3:2

6문항 친절형  [2,2,2]    L1/L2  L1/L2  L2/L3       L1:2 L2:3 L3:1
6문항 압박형  [2,2,2]    L1/L2  L2/L3  L2/L3       L1:1 L2:3 L3:2

9문항 친절형  [1,2,3,3]  L1  L1/L2  L2/L3/L3  L2/L3/L3   L1:2 L2:3 L3:4
9문항 압박형  [1,2,3,3]  L1  L2/L3  L2/L3/L3  L2/L3/L3   L1:1 L2:3 L3:5
```

모든 길이에서 페르소나 차이가 난이도 분포로 드러난다.

3문항에 예외 규칙을 둔 이유는, 토픽이 2개뿐이면 일반 규칙으로는
L3가 한 번도 안 나와서 압박형을 골랐는데 압박이 없는 세션이 되기 때문이다.

## 10. 문항 수 보장 — 예비 토픽

계획된 토픽을 다 썼는데 문항이 부족하면 예비 토픽을 투입한다.

```
예비 카테고리   문제해결, 직무역량, 실패·성장, 가치관·인성,
               프로젝트경험, 협업·갈등, 미래계획
               (계획에 이미 쓰인 것은 제외)
```

세션 시작 시 무작위로 섞어두고 필요할 때 앞에서부터 꺼낸다.

### 되묻기 한도

```
토픽당   1회. 되묻고도 부실하면 그 토픽의 꼬리질문을 포기하고 다음으로
세션당   3회. 넘으면 되묻지 않고 바로 다음으로
```

제한이 없으면 부실하게만 답하는 사용자에게 매 질문마다 되묻게 되어
면접이 아니라 추궁이 된다.

## 11. 임계값

```
1단계 게이트   발화 10초 미만 또는 25어절 미만이면 명백히 부실
되묻기         토픽당 1회 · 세션당 최대 3회
토픽당 최대    3문항 (주질문 1 + 꼬리질문 2)
```

1단계 게이트는 "네." 같은 명백한 케이스만 걸러내는 용도이므로
느슨하게 잡았다. 애매한 구간은 전부 LLM 판단으로 넘긴다.

**제한 시간 설정과 충돌하지 않는다.**
사용자가 응답 시간을 30초로 설정해도 10초 기준은 그대로 작동한다.
절대값 상한(예: 90초 초과면 충실한 답변) 방식이었다면
짧은 제한 시간에서 영원히 발동하지 않았을 것이다.

현재 값은 추정치다. 실제 면접 답변 데이터로 튜닝이 필요하다.
튜닝은 AI 파트에서 진행하며 다른 파트 코드에 영향이 없다.

## 12. 질문 응답에 담기는 값

AI 서버가 질문 하나를 만들 때마다 아래 형태로 내려준다.
뒤쪽에서 언급하는 필드 이름은 전부 여기 있는 것이다.

```
{
  "type": "question",
  "question_id": "q_4",
  "text": "왜 낙관적 락을 선택하셨나요?",
  "audio_url": "https://s3.../q_4.mp3",
  "category": "프로젝트경험",
  "difficulty": "L2",
  "question_number": 4,
  "question_total": 9,
  "topic_index": 2,
  "topic_total": 4,
  "is_spare_topic": false,
  "is_replay": false
}
```

### 필드 설명

```
type              질문의 종류
                  "question" 주질문 · "followup" 꼬리질문
                  "reask" 되묻기 · "session_end" 종료

question_id       질문 식별자. 답변 제출 시 이 값을 함께 보낸다
                  세션 안에서만 유일하다. 다른 세션과 겹칠 수 있다

reask_of          되묻기인 경우 원 질문의 question_id
                  되묻기가 아니면 null
                  리포트에서 되묻기 답변을 원 질문에 합칠 때 사용한다

text              화면에 표시할 질문 문장

audio_url         질문 음성 파일의 S3 URL
                  TTS 실패 시 null로 올 수 있다
                  null이면 텍스트 숨김 설정을 무시하고 텍스트를 표시한다

category          카테고리 8종 중 하나. 되묻기는 null

difficulty        "L1" | "L2" | "L3". 되묻기는 null

question_number   지금이 몇 번째 문항인가. 되묻기는 올라가지 않는다
question_total    사용자가 선택한 총 문항 수 (3 | 6 | 9)
                  진행률 표시에는 이 두 값을 쓴다

topic_index       지금이 몇 번째 토픽인가
topic_total       총 토픽 수. 세션마다 달라진다
                  참고용이며 진행률 표시에는 쓰지 않는다

is_spare_topic    문항 수를 채우려고 추가된 토픽에서 나온 질문인가
                  계획된 토픽이면 false
                  통계·디버깅용이며 화면 로직에 쓰지 않는다

is_replay         1회차와 동일한 질문인가
                  재연습이 아닌 일반 세션에서는 항상 false
                  회차 비교 화면은 이 값이 true인 질문만 표시한다
```

### 되묻기는 이렇게 온다

```
{
  "type": "reask",
  "question_id": "q_4r",
  "reask_of": "q_4",
  "text": "어떤 기술을 사용하셨는지 조금 더 말씀해 주시겠어요?",
  "audio_url": "https://s3.../q_4r.mp3",
  "category": null,
  "difficulty": null,
  "question_number": 4,
  "question_total": 9,
  "topic_index": 2,
  "topic_total": 4,
  "is_spare_topic": false,
  "is_replay": false

```

`question_number`가 올라가지 않는 것에 주의한다.
되묻기는 새 질문이 아니라 같은 질문의 재요청이다.

**`category`와 `difficulty`만 null이며 나머지 필드는 값이 온다.**
`is_spare_topic`과 `is_replay`는 되묻기에서 항상 false다.
모든 응답에 두 필드가 포함되므로 nullable 처리는 필요 없다.

## 14. 재연습 기준

### 1회차의 토픽 구조를 그대로 재생한다

재연습은 1회차와 **완전히 같은 모양**으로 진행된다.

```
주질문                1회차와 동일. 텍스트까지 그대로 재사용한다
                      예비 토픽에서 나온 주질문도 포함한다
토픽별 꼬리질문 개수   1회차와 동일하게 고정
꼬리질문 내용          매번 다르다. 새 답변을 읽고 만들기 때문이다
```

예시 — 1회차가 이렇게 진행됐다면

```
토픽1  주질문만 (되묻기 1회 발생)
토픽2  주질문 + 꼬리질문 2개
토픽3  주질문만 (되묻기 1회 발생)
```

2회차도 같은 모양이 된다.

```
토픽1  주질문만. 답변이 괜찮으면 바로 넘어가고, 부실하면 되묻는다
토픽2  주질문 + 꼬리질문 2개. 내용은 새 답변에 맞춰 새로 생성된다
토픽3  주질문만. 토픽1과 동일
```

**되묻기는 고정하지 않는다.** 2회차에 잘 답하면 되묻기 없이 넘어간다.
되묻기 여부는 그때그때 답변에 따라 결정된다.

### 왜 이렇게 하는가

토픽 구조가 같아야 회차 비교가 정확해진다.
1회차에 꼬리질문 2개를 받았던 주제에서 2회차에 5개를 받으면,
점수가 달라진 것이 실력 변화인지 질문 구성 변화인지 구분할 수 없다.

또한 **문항 수가 자동으로 맞는다.**
토픽별 문항 수가 1회차와 같으므로 합계도 같다.

### 항상 1회차를 기준으로 한다

3회차, 4회차도 직전 회차가 아니라 **1회차 구조**를 재생한다.

```
2회차   기준 = 1회차
3회차   기준 = 1회차
4회차   기준 = 1회차
```

직전 회차를 기준으로 하면 2회차에 나온 대체 질문이 3회차에 정식 질문이 되고,
회차마다 질문 세트가 불어나 1회차와 비교할 수 없게 된다.

**질문을 고정해야 오히려 비교가 자유로워진다.**
점수 비교는 직전 회차 기준으로 하며 회차 수 제한은 없다.
자세한 내용은 「리포트 생성 API 계약」 8장에 있다.

### 2회차에도 부실하게 답한 경우

되묻기 후에도 부실하면 그 토픽의 남은 꼬리질문을 포기한다.
답변에 파고들 내용이 없는데 억지로 꼬리질문을 만들면
"내 답변을 안 들었다"는 인상을 준다.

포기한 만큼은 대체 주질문으로 채워 문항 수를 맞춘다.
대체 질문은 1회차에 없던 것이므로 회차 비교 대상이 아니다.

### 재연습에서 옵션을 바꾼 경우

사용자가 문항 수나 페르소나를 변경하면 1회차 구조를 재생할 수 없다.

```
question_count 또는 persona가 원본과 다르다
  → 일반 세션으로 처리한다
  → 모든 질문의 is_replay가 false가 된다
  → 회차 비교 대상에서 제외된다
```

### 저장할 것 — 백엔드가 1회차 로그를 보낸다

**AI 서버는 1회차 로그를 보관하지 않는다.**
세션 상태를 임시로만 들고 있어 며칠 뒤 재연습을 누르면 찾지 못한다.

재연습의 진실 소스는 백엔드 DB이며,
세션 시작 요청에 `replay_log` 배열을 함께 보낸다.

```
replay_log에 담는 값
  question   type · text · category · difficulty · is_spare_topic
  followup   type · difficulty
  reask      담지 않는다. 재현하지 않는다
```

배열 순서가 곧 토픽 구조다. 형식은 「질문 생성 API 계약」 2장 참고.

- 재연습 시나리오 A — 2회차에 잘 답한 경우

    ```
    [1회차]  6문항 · 친절형
             토픽1 지원동기   주질문만        (되묻기 1회)
             토픽2 직무역량   주질문 + 꼬리 1개
             토픽3 협업·갈등  주질문 + 꼬리 2개

    [2회차]  같은 구조로 진행. 이번에는 전부 충분히 답함

    Q1  주질문 L1    백엔드 개발 직무에 지원하신 이유를 말씀해 주세요.
                     → 충분한 답변 (1회차에는 되묻기가 나갔던 질문)
    Q2  주질문 L1    가장 자신 있는 기술 스택은 무엇인가요?
                     → 충분한 답변
    Q3  꼬리질문 L2  (새 답변에 맞춰 새로 생성)
                     → 충분한 답변
    Q4  주질문 L2    팀원과 의견이 갈렸던 경험을 말씀해 주세요.
                     → 충분한 답변
    Q5  꼬리질문 L3  (새로 생성)
    Q6  꼬리질문 L3  (새로 생성)

    결과   6문항 · 주질문 3개 전부 1회차와 동일
           토픽별 꼬리질문 개수도 1회차와 동일
    ```

    1회차에 되묻기가 나갔던 Q1을 이번에는 한 번에 통과했다.
    같은 질문, 같은 구조이므로 개선 여부를 그대로 비교할 수 있다.

- 재연습 시나리오 B — 2회차에 부실하게 답한 경우

    ```
    [1회차]  위와 동일한 구조

    [2회차]  전부 부실하게 답함

    Q1  주질문 L1    백엔드 개발 직무에 지원하신 이유를 말씀해 주세요.
                     → 부실한 답변
        되묻기        → 여전히 부실
                     ※ 토픽1은 원래 꼬리질문이 없으므로 그냥 다음으로

    Q2  주질문 L1    가장 자신 있는 기술 스택은 무엇인가요?
                     → 부실한 답변
        되묻기        → 여전히 부실
                     ※ 토픽2의 꼬리질문 1개를 포기
    Q3  주질문 L2    예상치 못한 문제를 만나면 어떻게 접근하시나요?  [대체]

    Q4  주질문 L2    팀원과 의견이 갈렸던 경험을 말씀해 주세요.
                     → 부실한 답변
        되묻기        → 여전히 부실 (세션 한도 도달)
                     ※ 토픽3의 꼬리질문 2개를 포기
    Q5  주질문 L2    실패했던 경험을 말씀해 주세요.                [대체]
    Q6  주질문 L2    개발자로서 가장 중요한 가치는 무엇인가요?      [대체]

    결과   6문항 · 주질문 3개는 1회차와 동일
           Q3, Q5, Q6은 대체 질문이므로 회차 비교 대상 아님
    ```

### 회차 비교 대상

```
비교 가능   is_replay: true
            1회차에 나갔던 것과 동일한 주질문이다
            1회차에 예비 토픽에서 나온 질문도 여기 포함된다

비교 불가   is_replay: false
            꼬리질문 (내용이 매번 다르다)
            대체 질문 (1회차에 없던 것이다)
```

**필터는 `is_replay` 하나만 쓴다.** `is_spare_topic`으로 거르면 안 된다.
1회차 예비 토픽 주질문은 `is_spare_topic: true`이면서 `is_replay: true`이므로
비교 대상인데도 잘못 빠진다.

```
is_spare_topic   계획된 토픽에서 나왔는가, 채우기용 토픽에서 나왔는가
                 세션 내부 구조 정보. 통계·디버깅용이며 화면 로직에 쓰지 않는다

is_replay        1회차와 동일한 질문인가
                 회차 간 관계 정보. 비교 화면은 이것만 본다
```

## 15. 다른 파트가 반드시 알아야 할 것

```
1  진행률은 question_number / question_total 로 표시한다
   문항 수는 지켜지지만 토픽 수는 세션마다 다르므로
   topic_index는 진행률에 쓰지 않는다

2  되묻기(type: "reask")는 문항 수에 포함되지 않는다
   question_number가 그대로이므로 진행률을 올리지 않는다
   로그 테이블의 category, difficulty 컬럼은 NULL 허용

3  꼬리질문은 미리 만들 수 없다
   답변 제출 후 5~15초 대기가 발생한다. 로딩 표시 필요

4  재연습은 1회차의 토픽 구조를 그대로 재생한다
   주질문과 토픽별 꼬리질문 개수가 동일하다
   백엔드가 1회차 로그(replay_log)를 함께 보내야 한다

5  회차 비교는 is_replay가 true인 질문만 대상으로 한다
   is_spare_topic은 필터에 쓰지 않는다
   필드 설명은 12 참고

6  TTS 실패로 audio_url이 null이면 텍스트 숨김을 강제 해제한다
   숨김 상태에서 음성까지 없으면 면접을 진행할 수 없다

7  답변 제출에 video_url과 is_timeout을 함께 보낸다
   video_url은 리포트의 시선 축에 필요하다
   is_timeout이 true이면 되묻기를 하지 않는다
```
